## 写在前面

DVWA 大概是每个学 Web 安全的人第一个接触到的东西。但我发现身边不少人（包括之前的我）在它上面的做法是：把难度调到 Low，照着教程把 payload 敲一遍，看弹窗出来，截图，交报告。

这样做完，你大概能背下来几个 payload，但答不上来一个关键问题：**如果对方不是 Low 呢？**

所以这次我把进度推到 Medium，并且在每一个点上多问了一句"它到底拦了我什么"。下面按六个场景来写。目标环境是本地 `http://127.0.0.1/DVWA/`，PHP + MySQL，Burp Suite 抓包改包。

## 一、命令注入：`;` 被删掉之后

功能是一个 ping 工具：输入 IP，后端执行 `ping` 并把结果返回。源码逻辑大致是"把用户输入拼进系统命令"，没有任何转义。

最直接的打法：

```
127.0.0.1; ls
```

`;` 让 shell 把后半段当成新命令，于是 ping 结果后面跟出来一个目录列表。这一步很顺利。

但到了 Medium，同样的输入只会返回 ping 的结果——`;` 被过滤掉了。这里就是第一个容易踩的坑：**页面没报错、结果也正常，很容易让人以为是"防护有效"**。

实际上它做的是 `str_replace`，把 `&&` 和 `;` 删掉。于是换一个分隔符就通了：

```
127.0.0.1 | ls
127.0.0.1 & ls
127.0.0.1 || ls
```

管道、单与号、短路或，效果一样——都是让 shell 在当前命令之后继续执行。还有更省事的：

```
127.0.0.1%0als
```

换行符在 URL 编码后是 `%0a`，shell 同样把它当命令分隔符，而绝大多数黑名单都想不到要去拦换行。

**根因**：用户输入直接进了 shell。

**修复**：不要"过滤危险字符"，要"约束参数格式"。IP 字段就用正则校验成 IPv4 点分十进制；真要传参给系统命令，用 `escapeshellarg()` 包一层。黑名单和绕过是赛跑，你永远慢一步。

## 二、SQL 注入：引号被转义了怎么办

登录框背后的查询是字符串拼接，典型的：

```php
$query = "SELECT ... FROM users WHERE user_id = '$id'";
```

Low 下 `1' OR '1'='1` 直接把 `WHERE` 变成恒真，返回全部用户。

Medium 下它会转义引号（`mysqli_real_escape_string`）。这时候再发 `1' OR '1'='1`，引号变成了 `\'`，注入失败。

但这里有个更根本的问题：**这条查询的 `user_id` 是数字类型**。也就是说，我根本不需要引号：

```
1 OR 1=1
```

转义引号对数字型注入完全无效——因为整条 payload 里压根没有引号。这就是为什么"转义"只能算半个防护。

**修复**：预编译。`prepare` + `bind_param`，把参数和语句彻底分开，这才是从根上解决。转义只是避免了最表层的那一种写法。

## 三、盲注：把"是/否"当成一个信道

`sqli_blind` 页面不返回数据，只返回"用户存在 / 不存在"。看起来什么也拿不到。

但"存在"和"不存在"本身就是信息。只要我能构造一个条件，让它的真假取决于数据库内容，就能一位一位地把数据问出来：

```sql
1 AND SUBSTRING(database(),1,1)='d'   -- 页面正常 → 库名首字母是 d
1 AND SUBSTRING(database(),1,1)='a'   -- 页面异常 → 不是 a
```

一个字符猜几十次，一个库名几分钟。这就是布尔盲注，本质是把数据库的每一位压缩进"页面是否正常"这一个比特里。

实操上我用 sqlmap 跑通了整条链路，但它对我来说的价值是**验证判断**，不是替代理解。所以我后来把手写的 `SUBSTRING` 版本又跑了一遍——能自己写出判定条件，才算真的掌握。

还有一种变体是时间盲注：不看回显差异，看响应时间。

```sql
1 AND (SELECT 1 FROM (SELECT SLEEP(5))x)
```

延迟 5 秒就说明条件为真。适用于页面回显完全一致、连真假都分不出来的场景。

**修复**：预编译是基础；另外要统一错误响应（别让"用户不存在"和"参数错误"有不同的页面），必要时做请求频率限制和 WAF 规则。

## 四、文件上传：四层里少一层都不行

上传一个 `.php` 一句话木马，访问它，然后通过 `?cmd=` 执行系统命令——服务器就归我了。

这是六个里危害最直接的。它的根因不在"没校验后缀"，而在**校验的位置**：很多人只在前端用 JS 检查扩展名，抓包改一下请求就绕过去了。

正确的做法是四层叠加，缺一层都可能被绕过：

1. **后端**校验扩展名白名单（不是黑名单）和 MIME 类型；
2. 文件**重命名**为随机串，不保留用户上传的原始文件名；
3. 上传目录**禁止解析** PHP（Nginx 里 `location ~ \.php$ { deny all; }`）；
4. 文件存到 **Web 根目录之外**，用下载接口转发出去。

单看每一条都不完美——第 1 条能被伪造 MIME 绕，第 2 条能被双后缀绕——但只要四层都在，同时绕过的成本就高到不划算了。安全工程里这叫纵深防御。

## 五、六、XSS：反射型和存储型差在哪

反射型是最常见的：参数被原样回显到页面，构造一个带脚本的链接，诱导受害者点击。

```html
<script>alert('XSS')</script>
```

Medium 下它会替换 `<script`。绕过思路很直接——**不用 script 标签**：

```html
<img src=x onerror=alert(1)>
<svg/onload=alert(1)>
```

事件属性一样能执行 JS。或者混淆大小写 `<ScRiPt>`，因为替换是区分大小写的。

存储型的区别在于**持久化**：脚本存进数据库，每个访问页面的人都会中招，不需要你专门构造一个链接去骗人。所以我把它定为中危、反射型定为低危——不是技术难度不同，是**影响面和利用条件**不同。风险分级看的从来不是"技术多花哨"，而是"能造成多大损失、需要什么前提"。

**修复**：输出时做 HTML 实体编码（`htmlspecialchars`），配置 CSP，Cookie 加 `HttpOnly`。注意是**输出时编码**，不是输入时过滤——同一个字符串存进数据库，用在不同上下文需要不同的转义方式。

## 关于"三档防护"这件事

把这六个点串起来看，DVWA 的 Low → Medium → High 其实不是"安全性递增"，而是三种不同思路：

| | 做法 | 性质 |
| --- | --- | --- |
| Low | 什么都不做 | — |
| Medium | 替换/删除特定字符 | **黑名单** |
| High | 更长的黑名单、更严的校验 | 仍然是黑名单 |

黑名单的本质是"我列举出来的不让过"，而绕过者的工作量只是找到一个没被列举的写法。上面六个场景里，几乎每一个的 Medium 绕过都只花了几分钟。

真正有效的只有三类：**白名单**（只允许明确安全的）、**参数化**（不拼接）、**上下文编码**（按使用场景转义）。这三样共同点是——它们不试图猜测"什么是坏的"，而是规定"什么是好的"。

## 用扫描器，但别信扫描器

我还用 AWVS 扫了一遍，报了 8 个中高风险项。复核下来：

- 有 4 项和手工结果一致，确认；
- 有 2 项报了"反射型 XSS 高危"，但它需要用户主动交互、且没有持久化，按我的分级标准应该降到低危；
- 还有 2 项是靶场自带的 `phpinfo` 页面、目录列举，属于信息泄露但不可直接利用。

结论：扫描器的价值在于**不漏**，不在于**都对**。用它铺面、找线索，定级和写报告还得人来。

## 复盘

**两个坑**

第一个坑前面提过了：**页面报错不等于没有漏洞**。Medium 下按 Low 的 payload 打，结果"看起来正常"，我一度以为防护生效了。真正该做的第一件事是读源码，搞清楚它到底在哪一步、用什么方式过滤的。

第二个是盲注。一开始嫌 `SUBSTRING` 一个个猜太慢，直接上 sqlmap 出结果就收工了。但后来意识到，如果面试官问"你怎么判断这一位是真是假"，我是答不上来的。所以又回去手写了一遍。

**如果继续往下做**

- 写个脚本自动跑布尔盲注，不依赖 sqlmap（练的是判定逻辑，不是工具用法）；
- 加一节"这些 payload 用 WAF 规则怎么拦"，从防守方视角再走一遍；
- 环境和步骤固化成 Docker，别人能一键复现。
